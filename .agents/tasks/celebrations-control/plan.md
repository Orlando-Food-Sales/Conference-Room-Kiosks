## Decisions on the open points

1. **Remove vs hide: both, as two separate actions.**
   - **Hide** keeps the calendar untouched. It works for every listed person (birthdays others entered, anniversaries). Stored in `<dataDir>/celebration-hidden.json` (`data/` is gitignored, so deploys never overwrite it), written atomically (tmp file + rename) like `outfit-overrides.json`. Key = `kind:lowercased full name`. The door screens skip hidden people. A hide is reversible with **Show again**.
   - **Remove from calendar** deletes the whole yearly series with Graph `DELETE .../events/{id}` (lands in Outlook Deleted Items, recoverable). Allowed only for events the app can clearly recognise as its own: type `seriesMaster`, all-day, yearly recurrence (`absoluteYearly`), and a subject matching exactly `^<name> - Work Anniversary \(since (19|20)\d\d\)$` (no emoji or extra text), and the calendar reports `canEdit: true`. Birthdays other people entered are **hide-only** (the row says "Edit or delete this one in Outlook"). One-off and non-yearly events are listed only if they parse; never deletable. Reason: the app deletes only what it can prove it created in this format.
   - The server re-reads the event from Graph right before deleting and re-checks all of the above, so a stale list cannot delete a changed event.
2. **Add: included, both kinds.** Anniversary creates `<Name> - Work Anniversary (since YYYY)`. Birthday creates `<Name> - Birthday`. Both are all-day events with a yearly recurrence (`recurrence.pattern = {type:'absoluteYearly', interval:1, month, dayOfMonth}`, `range = {type:'noEnd', startDate}`). The anniversary's start date is the hire date, so its year is the "since" year. A birthday's start date uses the current year (no year is stored). Date and time zone are `birthdays.timeZone`. Before posting, the server checks that `parseCelebration(subject, 'full', date)` returns the same name and kind (so a name containing "birthday" or digits is refused), rejects names that are not 2 to 60 letters, spaces, `. ' ’ -`, rejects Feb 29, and rejects a duplicate kind+name (409). The write goes to the calendar chosen by the rule in step 2.
3. **Edit: not included.** Name or date changes are done as remove + add (or in Outlook). Reason: one more write path with parse risk and little value, since add and remove cover it.
4. **List:** everyone, sorted by next date, with a text search and a kind filter (All, Birthdays, Anniversaries). Hidden people stay in the list, dimmed with a "Hidden" tag. Each row shows name, kind, date (e.g. "Nov 17"), the upcoming count ("3 years" on the next date) or "birthday", days until, and calendar name. Only recognised yearly series (and future one-off events that parse) are listed. Anything else with the word birthday/anniversary is counted in `skipped` and the panel says "N other calendar entries are not shown".
5. **Series vs occurrence:** the app only ever works on the whole series. No single-occurrence delete.
6. **Read path:** new, separate from the door screens' 11-day calendarView. It reads `GET /users/{mailbox}/calendars/{id}/events?$select=id,subject,start,end,isAllDay,isCancelled,type,recurrence,seriesMasterId&$top=100` (up to 10 pages) over the same calendars the door screens use (`calendarIds`), so yearly series appear as one master each. Next date is computed from the recurrence month/day in the birthday time zone. It is loaded only when the panel opens or is refreshed, not on every dashboard refresh, and is not cached.
7. **Alerts or reminders: none.** Not clearly useful (leavers are removed on purpose; no one asked). Say so in the summary.
8. **Demo mode:** `CelebrationAdmin` keeps an in-memory demo list (about 8 people, dates relative to today, a mix of birthdays and anniversaries with `canEdit` true, calendar name "Calendar (demo)"). Add and remove change it for the life of the process. Hide still uses the real store. Demo door screens still show no celebrations (unchanged).
9. **Write calendar rule:** `BIRTHDAY_CALENDAR_ID` if set; otherwise the one calendar whose name equals `BIRTHDAY_CALENDAR_NAME` (case-insensitive); otherwise the only matched calendar; otherwise add is refused with "Several calendars match; set BIRTHDAY_CALENDAR_ID". Remove uses the calendarId on the list row, after checking it is among the calendars `calendarIds()` returns.
10. **No new settings**, so `.env.example` stays unchanged.

## API (all behind the existing `/api/admin/*` block in src/server.js, so token or session auth and same-origin JSON for sessions apply automatically)

- `GET /api/admin/celebrations` -> `{ enabled, demo, mailbox, calendars:[{id,name,canEdit}], people:[{id,calendarId,calendarName,kind,name,since,month,day,nextDate,daysUntil,upcomingYears,hidden,canDelete}], skipped, writeCalendar:{name,canEdit}|null, message }`. Not set up (no mailbox, not demo) -> 200 with `enabled:false` and a message.
- `POST /api/admin/celebrations/hide` `{kind,name,hidden}` -> `{ok}`. 404 if that person is not in the current list.
- `POST /api/admin/celebrations/add` `{kind,name,month,day,since?}` -> `{ok, person}`.
- `POST /api/admin/celebrations/remove` `{id,calendarId}` -> `{ok}`.
- Plain-language errors (status, text): read-only calendar 409 "This calendar is read-only for the app (canEdit is off), so nothing can be added or removed here. Give the app Calendars.ReadWrite on this mailbox, or use Hide."; `microsoft-down` 503 "Microsoft 365 is not answering right now. Nothing was changed. Try again in a few minutes."; `permission` 502 "Microsoft 365 refused the request. The app needs Calendars.ReadWrite on this mailbox (check the app's permissions)."; `not-found` 404 "Microsoft 365 could not find that mailbox or calendar."; unrecognised or changed event 409 "This entry is not in the app's own format, so the app will not delete it. Hide it, or delete it in Outlook."; bad input 400 with a specific sentence.
- Logging via `logger.log` with the new prefix `Celebrations:`, names and dates only, and who (same `who.via === 'session' ? who.session.email : 'the administrator token'` expression as `Tablet removed:`). Lines: `Celebrations: <Name> (Work Anniversary since 2019) removed from calendar "Calendar" by <who>`, `Celebrations: <Name> (Birthday) added ...`, `Celebrations: <Name> (...) hidden from the door screens by <who>`, `... shown again ...`. Refusals and Graph failures go to `logger.warn` (not the activity list).
